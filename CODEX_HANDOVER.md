# Главный принцип разработки

За время разработки было обнаружено, что большинство проблем возникает не из-за отсутствия функциональности, а из-за побочных эффектов изменений.

Поэтому:

* минимальные изменения лучше крупных;
* локальные фиксы лучше рефакторинга;
* существующий код менять только при необходимости.

# Известные проблемы прошлого

Эти ошибки уже встречались.

Если они появляются снова — вероятно произошёл регресс.

---

## Ошибка html_caption

Ошибка:

AttributeError:
Message has no attribute html_caption

Причина:

в используемой версии Aiogram поле html_caption отсутствует.

Решение:

использовать helper:

get_message_html_caption()

Никогда не использовать:

message.html_caption

---

## Ошибка unpack

Ошибка:

too many values to unpack

Причина:

после добавления formatted_text изменилось количество полей в SELECT.

При изменении запросов всегда проверять распаковку.

---

## Ошибка message too long

Ошибка Telegram:

message is too long

Причина:

лимит Telegram около 4096 символов.

Решение:

использовать answer_long_text()

---

## Ошибка metadata not found

Ошибка:

NameError
или
UnboundLocalError

Причина:

использование:

metadata["memory_id"]

в обработчиках поиска.

Важно:

metadata существует только после save_memory().

---

## Ошибка media group duplication

Ранее каждый элемент альбома сохранялся отдельной записью.

Сейчас это исправлено.

Нельзя возвращаться к старому поведению.

# Особенности интерфейса

Пользователь активно работает через кнопки.

Большинство функций доступны через inline keyboard.

Любая новая функция должна по возможности использовать существующий UX.

---

# Особенности удаления

Удаление памяти должно:

1. удалить запись из БД;
2. удалить связанные сообщения бота.

Простое удаление строки из БД считается неполным.

---

# Особенности редактирования

Редактирование должно работать для:

* текста
* фото
* видео
* кружков
* голосовых
* документов
* альбомов

Если функция работает только для текста — это считается неполной реализацией.

---

# Особенности поиска

Поиск должен работать независимо от типа контента.

Цель проекта:

найти информацию, а не файл.

Поэтому текстовые данные всегда важнее типа вложения.

# План оптимизации расходов

Проект должен стать прибыльным.

Текущая стратегия:

1. Rules-first категоризация.
2. GPT fallback only.
3. Минимизировать вызовы OpenAI.
4. Ограничивать бесплатный тариф.
5. Максимально использовать локальную логику.
6. Снижать расходы на STT.
7. Снижать расходы Railway.

Любое решение должно учитывать стоимость эксплуатации.
